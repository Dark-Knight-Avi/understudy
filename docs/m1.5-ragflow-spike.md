## 0. What this decides

[ADR-0007](./adr/0007-adopt-ragflow-for-retrieval.md) adopted RAGFlow *contingent
on this spike*. Three criteria, each with its own test below:

| # | Criterion | Test | If it fails |
|---|---|---|---|
| 1 | **Refusal** — an answer absent from the corpus is labelled ungrounded or refused (F7), never silently guessed | §6 | Failure *only here* → thin relevance-gate wrapper in front of RAGFlow, ~1 day (the `12-retrieval-and-rerank.md` design, reused) |
| 2 | **Per-user isolation** on the free tier — one user can never retrieve another's document text | §7 | Structural failure → **build retrieval ourselves**, ~12 d (the `10`–`13` design) |
| 3 | **Reachable over MCP** — OpenCode and Cline can query it, so documents are not chat-only (F10) | §8 | Structural failure → same fallback as 2 |

The stake, in schedule terms: **M5 is 2–4 days if all three pass, 12 days if 2 or
3 fail.** That asymmetry is why this single day is, per the delivery plan, "the
highest-leverage hour in the plan".

**A note on the eval set.** The delivery plan's M1.5 row says "run the eval set".
The eval set ([§7 of the delivery plan](./delivery-plan.md#7-parallel-tracks))
does not exist yet, and it would be built from real documents — which this spike
must not touch (see §1). So this procedure tests the *refusal criterion* with
synthetic documents, which is sufficient for a pass/fail verdict on criterion 1.
Measuring retrieval *quality* (recall@5, N7) stays where the eval set lives: M5.
The delivery-plan row should be corrected to match when the verdict is recorded.

## 1. Ground rules — N1 before anything is ingested

**No document text or source code leaves the network** (N1,
[ADR-0004](./adr/0004-egress-policy.md)). RAGFlow is third-party software with
defaults built for the open internet, and this spike runs *before* the M7/M8
egress lockdown, on a host that still has an open outbound route. Two rules make
that safe:

1. **The spike uses only synthetic documents.** Two dummy memos with canary
   strings, written in §5. No real report, no code, nothing anyone would mind on
   a search engine — *regardless* of how well the isolation below works.
2. **RAGFlow's containers get no route out, structurally.** The spike compose
   file puts RAGFlow and its datastores on networks with no egress path — the
   same `internal: true` construction the main stack uses — and §4 *verifies*
   that with a failed connection attempt and a packet-drop counter **before any
   document is ingested**. Verified, not asserted.

What RAGFlow would do by default, without rule 2 — each of these is a real
outbound flow in the upstream deployment, found while writing this procedure:

| Default | The N1 problem | How this spike closes it |
|---|---|---|
| The model-provider catalog is full of cloud vendors (OpenAI, etc.) — a user can paste a key and RAGFlow will happily send chunks to it | Document text leaves the network through a *user's* configuration choice | No egress route: such a provider fails to connect, structurally. §4.4 configures only the gateway and Infinity |
| Since v0.22 the image bundles **no embedding models**; upstream's default wiring points at a TEI container that downloads its model from Hugging Face at startup | Runtime downloads; and an unpinned model | We run no TEI. Embeddings come from our own Infinity on `.87`, already pinned and `HF_HUB_OFFLINE` |
| `HF_ENDPOINT` / Hugging Face fetches for optional parsers and rerankers | Runtime downloads mid-ingest | `HF_HUB_OFFLINE=1` in the container, and no route anyway. The spike leaves rerank at its default (off) |
| OpenTelemetry export if `OTEL_HOST` is set | Traces carry request metadata | Never set. Verify absent in §4.1 |
| Every datastore password defaults to `infini_rag_flow` | Not egress, but a default credential on the hub | `.env` requires generated secrets; compose has no working fallback values |

**And the standing rule of this fleet:** `.87` is the least contended box but it
is still someone's workstation. The spike stack is sized small (§3), and
`docker compose down -v` removes it completely (§9). If anything here fights the
person at the machine, the spike loses.

## 2. Preflight

Everything in this section is on `.87`, in the main stack's directory. Use
Terminal 1 for commands, Terminal 2 for watching logs.

### 2.1 The gateway answers, and `chat` exists

RAGFlow's generation model is `chat` through LiteLLM — "accepts any
OpenAI-compatible endpoint" is the property the whole ADR rests on, so prove the
endpoint first.

`▸ .87 — Terminal 1`

```bash
cd ~/understudy/deploy/host-87
# read single values; do NOT source .env — the exported-shell-variable trap
# (m1-runbook "If it breaks") makes later edits invisible to compose
MK=$(grep '^LITELLM_MASTER_KEY=' .env | cut -d= -f2-)
curl -s http://localhost:4000/v1/models -H "Authorization: Bearer $MK" | python3 -m json.tool
```

**Expect:** a JSON model list containing `"id": "chat"`. The catalog lives in the
database and is written by the fleet controller, so an empty list means the
controller is down or has withdrawn every rung — check the dashboard on `:8090`
and `docker compose ps fleet-controller` before going further. **Send me the
model list**, not "the gateway is fine": M2's defects were all invisible until
raw output disagreed with what everyone assumed.

### 2.2 Mint the spike's gateway key

RAGFlow gets a per-surface virtual key scoped to `chat`, never the master key
(docs/06 §8). Revoking it later kills exactly this spike's access.

`▸ .87 — Terminal 1`

```bash
curl -s -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $MK" -H 'content-type: application/json' \
  -d '{"models":["chat"],"key_alias":"ragflow-spike","metadata":{"surface":"ragflow-spike"}}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["key"])'
```

**Expect:** one line, `sk-...`. That value becomes `RAGFLOW_GATEWAY_KEY` in the
spike's `.env` (§3.1). If instead you get a JSON error, paste it — a 401 here
means the master key in `.env` is not the one the gateway is running with, which
is the shell-variable trap again.

### 2.3 Embeddings — bring up `infinity-embed` if it is not already up

M1 deliberately excluded embeddings, so on most days this service has never
started. RAGFlow cannot embed without it (the v0.27 image bundles no models).

`▸ .87 — Terminal 1`

```bash
docker compose ps infinity-embed
```

**If it shows `Up (healthy)`:** skip to §2.4.

**If not:** the weights must be on disk first — `HF_HUB_OFFLINE=1` is an egress
control, and it means the service will not fetch anything itself. Pull them once,
into the named cache volume, with a throwaway container (this one *is* allowed
out; it is the documented pre-download path, and the host's outbound route is
still open until M8):

```bash
docker run --rm -e HF_HOME=/cache/huggingface \
  -v aiplatform-87_infinity_cache:/cache/huggingface \
  --entrypoint python michaelf34/infinity:0.0.76 \
  -c "from huggingface_hub import snapshot_download; print(snapshot_download('Qwen/Qwen3-Embedding-0.6B'))"
```

**Expect:** several minutes of download bars, then a path ending
`snapshots/<40-hex-characters>`. **Copy that 40-character hash** — it is the
pinned revision `.env.example` has been waiting for:

```bash
setenv() { grep -q "^$1=" .env && sed -i "s|^$1=.*|$1=$2|" .env || printf '%s=%s\n' "$1" "$2" >> .env; }
setenv EMBEDDINGS_REVISION <the-40-hex-hash>
docker compose --env-file .env up -d infinity-embed
docker compose logs -f infinity-embed        # Ctrl-C once it settles
```

**Verify — the service answers from inside the network** (it has no published
port, deliberately: `internal: true` silently ignores `ports:`, so it never got
one):

```bash
docker compose exec infinity-embed python -c \
  "import urllib.request as u; print(u.urlopen('http://127.0.0.1:7997/models', timeout=5).read().decode()[:300])"
```

**Expect:** JSON naming `Qwen/Qwen3-Embedding-0.6B`. If the container restarts
in a loop instead, read its log: `--revision=` with an empty value, or weights
missing from the cache volume, both land here. Also glance at
`nvidia-smi` — embeddings take ~1.2 GB and this host's sharing table
([`03-gpu-sharing-policy.md`](./03-gpu-sharing-policy.md) §3) must still hold.

### 2.4 Elasticsearch's kernel prerequisite

RAGFlow's default document engine is Elasticsearch, which refuses to boot below
`vm.max_map_count=262144`. WSL2's default is lower.

`▸ .87 — Terminal 1`

```bash
cat /proc/sys/vm/max_map_count
sudo sysctl -w vm.max_map_count=262144
echo 'vm.max_map_count=262144' | sudo tee -a /etc/sysctl.conf   # survive wsl --shutdown
```

**Expect:** the first command likely prints something like `65530`; after the
second, re-`cat` prints `262144`. Skipping this produces an es01 container that
exits within seconds with `max virtual memory areas ... too low` buried in its
log — cheap to prevent, annoying to diagnose.

### 2.5 Docker's resolver is the campus one

Campus DNS blocks the public resolvers and WSL's stub resolver is unreachable
from containers ([`05-host-setup.md`](./05-host-setup.md) §5 — the
`daemon.json` block). The image pulls in §3 die with `Name does not resolve`
without this, and it reads as an outage rather than a configuration gap.

`▸ .87 — Terminal 1`

```bash
cat /etc/docker/daemon.json
```

**Expect:** a `"dns"` key listing the campus resolvers (the same servers Windows
uses — `Get-DnsClientServerAddress -AddressFamily IPv4` in PowerShell if you need
to re-derive them), alongside `insecure-registries`. If `dns` is missing, follow
docs/05 §5 to add it — and remember the order-matters warning there about
`nvidia-ctk`.

## 4. Close the doors — verify *before* any document goes in

Nothing gets ingested — even synthetic — until 4.2 shows the failure it is
supposed to show. This is the N1 discipline: the boundary is proven by a test,
never by reading the compose file and nodding.

### 4.1 The containers are on exactly the networks the file says

`▸ .87 — Terminal 1`

```bash
docker inspect ragflow-spike-ragflow-1 --format '{{range $k,$v := .NetworkSettings.Networks}}{{println $k}}{{end}}'
docker inspect ragflow-spike-es01-1    --format '{{range $k,$v := .NetworkSettings.Networks}}{{println $k}}{{end}}'
docker inspect ragflow-spike-ragflow-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -Ei 'OTEL|HF_|PROXY' ; echo "-- end env grep --"
```

**Expect:** `ragflow` lists exactly three networks — `aiplatform-internal`,
`ragflow-spike-internal`, `ragflow-spike-lan`; `es01` lists exactly one —
`ragflow-spike-internal`. The env grep shows `HF_HUB_OFFLINE=1` and **no**
`OTEL_HOST`, no proxy variables. Anything extra is a finding — paste it.

### 4.2 An outbound attempt fails

`▸ .87 — Terminal 1`

```bash
# a public address, by IP, so DNS cannot confuse the result
docker compose exec ragflow python3 -c \
  "import urllib.request as u; u.urlopen('http://93.184.216.34', timeout=5)" \
  ; echo "exit=$?"
# and by name, which also probes the DNS channel
docker compose exec ragflow python3 -c \
  "import urllib.request as u; u.urlopen('https://huggingface.co', timeout=5)" \
  ; echo "exit=$?"
```

**Expect:** both fail — timeout or unreachable, `exit=1`. **That failure is the
pass.** If either *succeeds*, STOP: the container has a route out, no document
of any kind gets ingested, and the network block in the compose file needs
re-reading against what §4.1 printed. (The name lookup itself may resolve — the
embedded DNS forwards through the daemon — but the connection must die. DNS
exfiltration is a channel the M8 lockdown addresses fleet-wide; for a spike on
synthetic documents, a dead connection path is the bar.)

### 4.3 Clamp the published-port network and watch the counter

`spike-lan` exists only so `ports:` works (see the trap above). It is a normal
bridge, so it has a route out — clamped the same way the main stack clamps its
`lan` network: pinned subnet, DOCKER-USER rules, and the rules are the
enforcement while the pinned subnet is what makes them mean something.

`▸ .87 — Terminal 1`

```bash
sudo iptables -I DOCKER-USER -s 172.28.10.0/24 -d 10.0.0.0/24 -j RETURN
sudo iptables -I DOCKER-USER -s 172.28.10.0/24 -d 10.0.1.0/24 -j RETURN
sudo iptables -A DOCKER-USER -s 172.28.10.0/24 -j DROP
sudo iptables -L DOCKER-USER -v -n | grep 172.28.10
```

(Substitute the real internal prefixes — and *derive* them per
[`ports.md`](./ports.md): ours turned out to be `/23`, and a `/24` rule covers
half the subnet while looking correct.)

**Expect:** the three rules listed, counters at or near zero. Re-run the §4.2
probes, then re-list: **the DROP counter must have moved and the probes must
still fail.** Keep this command handy — you will read the counter again at §9,
after the tests, and any growth beyond your own probes is a finding.

> These rules do not survive a WSL restart. That is fine for a one-day spike;
> making them permanent is M8's job, done fleet-wide and properly.

### 4.4 Point RAGFlow's models at *our* endpoints, and nothing else

In the browser (`http://localhost:9390`, as `spike-admin`):

1. Avatar → **Model providers** → add **OpenAI-API-Compatible**:
   - **Chat model** — name `chat`, base URL `http://litellm:4000/v1`, API key =
     the §2.2 virtual key. (Service name, not IP: RAGFlow reaches the gateway as
     a sibling on `aiplatform-internal`, exactly like every other platform
     container.)
   - **Embedding model** — name `Qwen/Qwen3-Embedding-0.6B`, base URL
     `http://infinity-embed:7997`, API key = `INFINITY_KEY`. If the form insists
     on a path, try `http://infinity-embed:7997/v1`; record which one worked.
2. **System model settings** → default chat = `chat`, default embedding = the
   Infinity entry.
3. Configure **no other provider**. The cloud vendors in the catalog stay
   unconfigured — and could not work anyway, per 4.2, which is the point.

**Verify with a round trip, not the settings page:** open a chat with any
assistant-less default (or wait for §6's assistant) — a reply proves
`ragflow → litellm → vLLM` works end to end. If the provider form's "test"
button fails, paste the ragflow log lines from Terminal 2; a 401 there is the
virtual key, a connection error is a network-membership problem from §4.1.

## 6. Test 1 — refusal (criterion 1)

**The question:** when the corpus does not contain the answer, does RAGFlow say
so — or does it guess, or worse, guess with a citation? An assistant that
invents a citation is worse than one that admits ignorance.

**Setup**, in the browser as `spike-admin`:

1. Create a knowledge base `spike-kb`, embedding model = the Infinity entry,
   chunk method **General**. Upload `memo-junction5.txt`, run parsing, wait for
   **SUCCESS**. (Watch Terminal 2 while it parses — an embedding failure
   surfaces here first, and §4.2 means it *cannot* be quietly rescued by a cloud
   fallback.)
2. Create a chat assistant on `spike-kb`. In its configuration set the **empty
   response** field to exactly: `NOT IN CORPUS`. Leave the similarity threshold
   at its default. Note the threshold value down — it is part of the evidence.

**The three probes**, asked in that assistant's chat, one at a time:

| # | Ask | Pass looks like | Fail looks like |
|---|---|---|---|
| A | "What was the average delay at Junction 5 before retiming?" | `84 seconds`, **with a citation** pointing at `memo-junction5.txt` | A right answer with no citation, or a wrong number |
| B | "What is the substation limit at the bus depot?" (that memo is **not** in this KB) | `NOT IN CORPUS`, or an explicit "the knowledge base does not contain this" | Any kW figure. A *fabricated* figure with a citation to the junction memo is the catastrophic form — screenshot it if it happens |
| C | "What was the delay at Junction 9?" (adjacent to real content; retrieval will find *weak* matches) | Refusal, or an answer that explicitly says Junction 9 is not covered | The Junction **5** numbers presented as Junction 9's, cited |

Probe C is the one that actually decides the criterion: B tests the empty-recall
path, C tests the weak-recall path, and most RAG tools that fail, fail on C.

**Then re-run B and C once with the empty-response field cleared**, to record
what RAGFlow does when an operator forgets to set it — that default behaviour
determines whether adoption needs a "must configure" checklist item or a
wrapper.

**Pass/fail:** criterion 1 **passes** iff A is cited-correct and B and C both
refuse or explicitly disclaim, *with the empty-response field set*. The
cleared-field re-run does not affect pass/fail; it goes in the verdict notes.

**Evidence to capture:** screenshots of all three answers (plus the two
re-runs), the similarity threshold used, and the exact empty-response text.
Send the screenshots, not a summary — the wording of a near-refusal matters.

## 7. Test 2 — per-user isolation (criterion 2)

**The question:** users upload their own files; can user B ever read user A's?
A silent cross-tenant read is the worst failure available to this product.

**Setup:**

1. In a **private/incognito window** (so the sessions cannot bleed), register a
   second account, `spike-user-b`, via the same self-registration form.
2. As `spike-admin` (user A): upload `memo-depot.txt` into `spike-kb` — A's
   corpus now holds both canaries.
3. As `spike-user-b` (user B): create B's own KB `b-kb` with one trivial
   document (paste a few sentences; content irrelevant).

**The probes, as user B:**

| # | Probe | Pass | Fail |
|---|---|---|---|
| A | Knowledge-base list in the UI | Only `b-kb` visible | `spike-kb` visible at all |
| B | Ask B's assistant: "What is reference CANARY-ALPHA-7Q4X9?" and "What is the substation limit of the depot?" | Refusal / not found — B's corpus cannot answer | Any answer containing `84 seconds`, `640 kW`, or either canary |
| C | API level — the UI can lie by omission, the API is the surface MCP uses. As **B**, create an API key (avatar → API), then from Terminal 1: | | |

`▸ .87 — Terminal 1`

```bash
BKEY=<user B's API key, from the UI>
# B's view of the world:
curl -s http://localhost:9380/api/v1/datasets -H "Authorization: Bearer $BKEY" | python3 -m json.tool
# Direct retrieval against A's dataset id (read the id from A's UI URL, or from
# A's own /datasets listing with A's key):
curl -s -X POST http://localhost:9380/api/v1/retrieval \
  -H "Authorization: Bearer $BKEY" -H 'content-type: application/json' \
  -d '{"question":"CANARY-ALPHA-7Q4X9","dataset_ids":["<A-dataset-id>"]}' \
  | python3 -m json.tool
```

**Expect:** the listing shows only B's dataset; the direct retrieval returns an
authorisation/not-found **error**. **Fail:** any response whose body contains
`CANARY-ALPHA-7Q4X9` chunk text — that is a cross-tenant read, criterion 2 is
dead, and per ADR-0007 the fallback is building retrieval ourselves.

**Also record** (verdict notes, not pass/fail): whether RAGFlow's "team" sharing
feature exists in this build and whether its default is *unshared* — deliberate
sharing is a feature, defaulting to shared would be a finding.

**Evidence:** both curl outputs verbatim, plus a screenshot of B's KB list.

## 11. If it breaks

| Symptom | First thing to check |
|---|---|
| `docker compose pull` fails with `Name does not resolve` | §2.5 — the campus-DNS `daemon.json` gap. Not an outage |
| A pull fails with `manifest unknown` | The pinned tag genuinely does not exist upstream — the `searxng` failure mode. Verify against Docker Hub *by hand* and fix the pin; do not reach for `latest` |
| `curl` to 9380/9390/9382 returns `000` | The `ragflow` service is missing its `spike-lan` network: `internal: true` **silently ignores** `ports:` — healthy container, empty PORTS column. The M1 classic |
| An `.env` edit (password, `RAGFLOW_API_KEY`) seems to change nothing on recreate | You sourced `.env`; **exported shell variables beat `--env-file`**. `exec bash`, re-run. Read values with `grep`/`cut`, never `set -a` |
| es01 exits within seconds | §2.4 — `vm.max_map_count`. Its log says so, quietly |
| es01 returns 401 to its own healthcheck | Password changed after first boot; ES stored the old one in `esdata`. `down -v`, redo §3.2 |
| ragflow log: cannot connect to `nats` (or another service not in this stack) | v0.27's optional Go pipeline wants NATS. Add upstream's `nats:2.14.2` service to the spike compose on `spike-internal`, `up -d`, note the addition in the verdict — it changes the fold-back footprint |
| ragflow crash-loops trying to reach `mysql`/`minio`/`redis`/`es01` | Those names are load-bearing: the image's baked-in config template defaults to them. If you renamed a service, rename it back |
| Provider "test" fails against `http://litellm:4000/v1` | `ragflow` not on `aiplatform-internal` (§4.1), or the virtual key — check ragflow's log for the status code: 401 = key, timeout = network |
| Embedding fails during parsing | Base-URL path shape (§4.4 — try with and without `/v1`); or `infinity-embed` down; or the model *name* in the form does not match what `/models` reported in §2.3 |
